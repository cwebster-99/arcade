# Universe demo — setup & runbook

A ~10 minute GitHub Copilot App demo showing **Connectors**, **Computer Use**, **Image Generation**, and the **Library**.

**Story:** a recent Copilot App release has a session startup problem. Resuming local sessions is timing out, mostly on Windows.

- **Act 1, Sentry (real data):** you paste a link to the real Copilot App Sentry issue for the session-resume timeout. Copilot auto-discovers the **Sentry connector** and pulls the issue details, including the release, the OS breakdown, and related create/resume issues. It then explains what's going on. If real Sentry data can't be shown, use the [offline fallback](#offline-fallback-for-act-1-arcade-sentry-crash).
- **Act 2, Dashboard and Computer Use:** you ask Copilot to add a "session ready time" panel, filtered by app version, to the team's **Session Startup Health** dashboard. Copilot does this through the **Copilot App Telemetry connector**, which is a local MCP server. It then uses **Computer Use** to open the live dashboard and check its work. The **first check fails** because the panel shows an error. Copilot fixes the query and checks again, and this time the regression on 1.1.28 Windows resume is visible.

> ⚠️ This file describes the planted behaviors. If the agent reads it during the live demo, the surprise is gone. Don't point the agent at `demo/`, and keep prompts focused on Sentry and the dashboard.
>
> All dashboard data in this repo is **synthetic** and generated by `scripts/generate-data.js`. Don't commit real Sentry issue IDs, event counts, or user counts here. Keep the hero issue link in your private presenter notes.

## One-time setup

### 1. Install the dashboard and connector

```bash
cd demo/telemetry-dashboard
npm install          # Node 18+
npm start            # http://localhost:4319
```

Leave the server running. The page auto-refreshes over server-sent events whenever `dashboard.json` changes or new events are ingested.

### 2. Register the MCP connector

Print the snippet with this machine's absolute path:

```bash
cd demo/telemetry-dashboard && npm run mcp:config
```

Merge the output into `~/.copilot/mcp-config.json` (Windows: `%USERPROFILE%\.copilot\mcp-config.json`):

```json
{
  "mcpServers": {
    "copilot-app-telemetry": {
      "type": "local",
      "command": "node",
      "args": ["<ABSOLUTE PATH>/demo/telemetry-dashboard/mcp-server/server.js"],
      "tools": ["*"]
    }
  }
}
```

If an older `arcade-telemetry` entry is in that file, remove it. Restart the Copilot App or CLI. You should see these tools: `get_dashboard`, `list_metrics`, `add_panel`, `update_panel`, and `remove_panel`. To smoke-test the server from the command line, run `npm run test:mcp`.

### 3. Sentry access (Act 1)

Make sure the presenter account can open the Copilot App Sentry project and the hero issue in a browser. Make sure the Sentry connector can be installed in the Copilot App, because it will be auto-discovered live. Keep the hero issue URL, and optionally the related create-timeout and runtime-RPC issues, in your private notes.

### 4. Dry run (optional, takes a few seconds)

With the dashboard running:

```bash
cd demo/telemetry-dashboard && npm run verify
```

This adds a panel through MCP using the legacy field and confirms the panel renders the error. It then fixes the panel, confirms data renders, checks `/ingest`, and **resets the dashboard**.

## Planted behavior: the legacy `version` field trap (Act 2)

The dashboard has a `$app_version` variable (a dropdown with All, 1.1.26, 1.1.27, and 1.1.28). The existing panels come from the older events pipeline and filter with a **legacy field name**:

```
metric=startup_error | where version = $app_version | count by reason
```

The `session_ready_ms` events come from the new pipeline and only have **`app_version`**. They also have `operation` (create/resume), `os_platform` (windows/macos), `session_type`, `outcome` (ready/timeout), and `value`. This is how the trap plays out:

- `list_metrics` returns metric names and descriptions only, with no field schemas. `add_panel` and `update_panel` **never validate** fields, so writes always succeed.
- An agent that copies the existing panels' pattern writes something like:
  `metric=session_ready_ms | where version = $app_version | p95 by operation`
- The rendered dashboard shows that panel with a red border and:
  **`No data — unknown field 'version' for metric session_ready_ms (did you mean app_version?)`**
  The error appears for every dropdown value, including "All".
- The error is visible **only** in the rendered UI, so the first Computer Use check fails on screen. Copilot then calls `update_panel` with `where app_version = $app_version`, checks again, and the chart renders.

### What the fixed panel shows (synthetic data)

| 1.1.28 vs 1.1.27 | p50 | p95 |
| --- | --- | --- |
| resume, windows | ~1.3s → **~3.9s** | ~2.2s → **30s (timeout cap)** |
| resume, macos | unchanged (~1.0s) | unchanged |
| create, windows/macos | unchanged (~1.9–2.4s) | roughly unchanged |

On 1.1.28, `Startup errors by reason` is dominated by `timeout`. Good follow-up asks: "break it down by `os_platform`", or "show p95 by operation". Timeouts are recorded as `outcome=timeout` with `value=30000`.

`data/events.json` holds about 4,300 events covering 14 days. Timestamps are shifted at load time so the newest day is always "today". Run `npm run generate-data` to regenerate them deterministically.

## Offline fallback for Act 1: arcade Sentry crash

Use this if the real Copilot App Sentry data can't be shown, for example because of no network, an account problem, or data that can't be shared. It tells the same Act 1 story against this arcade app: v1.4.0 "shipped" Snake swipe controls that crash on mobile.

### Setup

1. Create a free Sentry org at <https://sentry.io>, then a **React** project named `arcade`.
2. In the repo root, run `npm install`, then `cp .env.example .env`. Set the following:
   ```ini
   VITE_SENTRY_DSN=https://<key>@o<id>.ingest.sentry.io/<project>
   SENTRY_DSN=https://<key>@o<id>.ingest.sentry.io/<project>
   SENTRY_ORG=<your-org-slug>        # optional; used to print a direct link
   ```
3. Run `npm run seed:sentry`, or `node scripts/seed-sentry-crash.mjs --dry-run` to preview. This sends 30 synthetic events for the touch crash on release `arcade-games@1.4.0`. They come from iOS Safari, iPadOS, and Chrome Android, across 6 users, with stack frames pointing at the real file and line. It also sends 6 unrelated low-volume errors on 1.3.0. Run it again on the morning of the demo so the issue looks fresh. Save the URL of the `TypeError … clientX` issue.
4. Optional: run `npm run dev` with `VITE_SENTRY_DSN` set. To reproduce the crash for real, open Snake with Chrome DevTools device emulation and swipe on the board.

### The planted crash

`src/components/SnakeGame.tsx`, in `handleTouchEnd`:

```ts
const touch = event.touches[0];
const dx = touch.clientX - start.x;   // touches is empty on touchend
```

During `touchend`, `event.touches` lists only the fingers still on the screen, so it's empty. Chrome reports `Cannot read properties of undefined (reading 'clientX')` and Safari reports `undefined is not an object (evaluating 'touch.clientX')`. Desktop and keyboard play, and the existing tests, are unaffected. **The fix** is to use `event.changedTouches[0]`. There are no code comments flagging the bug.

## Query language reference

```
metric=<name> [| where <field> (=|!=) <value|$var|"quoted"> [and ...]] [| <agg>[(field)] [by <field>]]
```

- `agg` is one of `count` (the default), `avg`, `sum`, `min`, `max`, `p50`, `p90`, or `p95`. Numeric aggregations use `value`.
- `day` is a derived field (`YYYY-MM-DD`) that works with every metric, for example `count by day`.
- `viz` is one of `stat`, `bar`, `line`, or `table`. `width` is the number of grid columns out of 12.
- A variable set to `All` skips that filter, but field validation still applies.
- Ingest endpoint: `POST http://localhost:4319/ingest` with a JSON event or an array of events, each with a `metric` string.
